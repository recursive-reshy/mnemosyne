# Checkpoint C plan: Phase 4 (ownership)

## Context
Checkpoints A and B left a baseline with users, sessions and sign-in, and every `/api` route behind `requireUser`, but no data table has an owner. Checkpoint C (ADR 0062, 0065; TRD §3.2, §3.4, §5, §11.1) gives every data table a `user_id`, makes every repository function take `userId` first, threads the user through services, controllers and background code, and ends with module gating. At the end both guard tests (`database.schema.test.ts`, `signature.guard.test.ts`) have empty "unconverted" lists. Tasks run in order 4.1 → 4.6; each is one commit (`feat(0.9-4.x): …`, co-author trailer), pushed. After each task run `pnpm test`, `pnpm lint`, `pnpm typecheck` in `apps/server` (shared and web aren't touched; API shapes are unchanged except new 404s). `pnpm e2e` is not required before F and is already failing until 8.1; say so in the report.

Every task follows the same pattern, described once:
1. **Schema:** edit the baseline in `repositories/database.ts` in place: `user_id TEXT NOT NULL REFERENCES users ( id ) ON DELETE CASCADE` as the second column, per-user unique/list indexes from TRD §3.2. Remove the task's tables from `UNCONVERTED` in `database.schema.test.ts` and its repositories from `UNCONVERTED` in `signature.guard.test.ts` in the same commit (each guard fails if the list and the schema disagree).
2. **Repositories:** `userId` first on every exported function (including the unused ones: `clearJobs`, `listLinkRuns`, `deleteForJob`, the postings functions, etc.); `user_id = ?` in every `WHERE`/join, `user_id` in every `INSERT`; update/delete by ID is `WHERE id = ? AND user_id = ?`. Functions with a destructured first argument (`listDue( { … } )`) get a separate `userId` first, because the guard reads the parameter name.
3. **Services/controllers:** `userId` first; controllers pass `currentUser( req ).id`; "no row" is `NotFoundError` with the same message as an unknown ID.
4. **Tests first (red):** a two-user repository isolation test per repository (seed A and B; every read, list, update and delete with B's ID never returns or changes A's rows); route isolation tests (A's IDs requested as B → 404, same body as an unknown ID); per-user uniqueness (same natural key allowed for two users). Tests need users because foreign keys are on: repository tests call `createTestUser()` from `test-support/auth.ts` (twice for isolation). Red = missing `user_id`/signature; green = conversion. Existing tests may change only per TRD §11.1 (signing in, passing a user, per-user fixtures); list every changed file in the `tasks.md` log line.

## Decisions to confirm (not settled by the TRD/ADRs)
1. **Cross-user queries move to `system.repository.ts` early.** The loops need queries with no user (oldest runnable job, expired jobs, due feeds, restart requeue, next Melete note). The signature guard bans them in converted repositories, and the TRD only creates `system.repository.ts` in 5.4. Plan: the task that converts each table moves its cross-user functions into `system.repository.ts` (already exempt in the guard) with **today's semantics** (oldest first, no eligibility, no round-robin), each returning `user_id`; background code then uses the row's `user_id`. 5.4 replaces them with `claimNextJob` / `claimNextGeneration` / `listDueFeeds` etc. per TRD §6.1. This is ordering, not a design change.
2. **A temporary owner shim in 4.1 only.** Prompt/settings reads become per-user in 4.1, but jobs, feeds and Melete notes get their `user_id` only in 4.2, 4.3 and 4.5. Background code in between (worker, intake poller, Melete generator/scan, health) has no row to read the owner from. Plan: one clearly marked file `services/interimOwner.ts` exporting `interimOwnerId()` (the admin's ID; throws if none), used only by those background call sites, removed progressively (jobs paths in 4.2, feeds/Gmail paths in 4.3, Melete in 4.5) and gone with its test in 4.6. HTTP paths use the real user from the start. Alternative would be reordering tasks, which the task file forbids.
3. **`vaultRootFor( userId )` stub** (4.2) takes the user's ID, not the `user` object the TRD sketches; 5.1 makes it look up `vault_dir` itself via `findUserById`, so background callers never need a user object. It returns `config.vaultPath` until then.
4. **Agent health row no longer depends on the linking setting.** `isLinkingEnabled()` becomes per-user in 4.1, but the agent check is an app check. From 4.1 the agent is checked whenever `config.agent !== null`, and the status row is `off` only when it is null. (Per-user "linking off" stays enforced where jobs are linked.)
5. **Health reads use positional args**, e.g. `listHealth( userId, includeApp )`, not the `{ userId, includeApp }` object of TRD §3.4, because the guard parses the parameter name `userId`.
6. **`POST /api/status/refresh` as a member** runs no app checks and returns the member's own status (no 404); as the admin it runs them. `POST /api/backups` is admin-only (404 for members); `GET /api/status/:kind/:id/errors` for an app kind is 404 for members.
7. **Settings by module (4.6):** `GET /api/settings` keeps its shape; a `PUT` containing a key that belongs to a module the user lacks is a 404 for the whole request (nothing saved), the same rule as TRD §5.4.
8. **`usage_events` stays in 6.2**, where `tasks.md` puts it; Phase 4 only makes sure all four run tables have `user_id` (summary/link runs in 4.2, extraction runs in 4.3, Melete runs in 4.5).

## 4.1 Prompt profiles, settings, app settings
- **Schema:** `prompt_profiles`, `prompt_versions`, `settings` get `user_id`; `settings` PK `( user_id, key )`; `prompt_profiles_active_name` unique on `( user_id, purpose, lower( name ) ) WHERE deleted_at IS NULL`; any unique index on `seed_key` becomes per user (check the baseline first).
- **Tests first:** isolation tests for `promptProfiles.repository` and `settings.repository` (including two users with the same profile name and same setting key); `seedUser` per user (each user gets their own full set, own `default_profile_id`; a second user doesn't touch the first; one transaction, rolls back on failure); `appSettings` get/set; `getFeedCheckInterval()` reads `app_settings` (default 60); route tests: user B cannot read, rename, delete, save a version of, or restore A's profile (404); `PUT /api/settings` with `feed_check_interval_minutes` from a member is a 404 and saves nothing, from the admin it works; two users with different `default_model` see their own.
- **Code:** convert `promptProfiles.repository.ts` (12 functions) and `settings.repository.ts`; `appSettings` already exempt. `seedUser( userId, now )` becomes the real per-user seeder (`seedSharedProfiles` deleted); remove its call from `test-support/database.setup.ts`, so tests get profiles via `createTestUser`. Thread `userId` through `prompts.service`, `settings.service`, `models.service` (`listModels`, `assertKnownModel`), their controllers (`promptProfiles`, `settings`, `models`), and every caller that reaches them: `jobs.service` (`validateChoices`, `toSummaryUsage`, `defaultFolderFor`, `saveJob`'s `setLastFolder`, `completeSummary`'s linking check — via the HTTP user, or the shim in worker paths), `inbox.service`, `feeds.service`, `gmailSources.service`, `meleteReview`/`meleteGeneration`/`melete*` services (`getLearningRoot`, model resolvers), `worker/summarizeJob.ts` and `worker/linkJob.ts` (shim), `health.service`/`status.service` (decision 4). `feed_check_interval_minutes` is read/written through `app_settings`; `updateSettings( userId, role, body )` rejects it for non-admins. `resetScanClock()` call in `updateSettings` stays global until 4.5.
- **Existing tests expected to change:** the 10 core files (profiles/settings/appSettings repos; prompts, settings, models, seedUser services; three route tests) plus `jobStore.repository`, `linkSuggestions.repository`, `linkRuns.repository`, `meleteRuns.repository`, `database`, `jobs.service`, `linkJob`, `summarizeJob` tests that relied on pre-seeded profiles (they switch to `createTestUser`). List each.
- **Commit:** `feat(0.9-4.1): per-user prompt profiles and settings`.

## 4.2 Jobs, runs, link suggestions, review, save
- **Schema:** `jobs`, `summary_runs`, `link_runs`, `link_suggestions` get `user_id`; add `jobs_user_status ( user_id, status, created_at )` and `jobs_user_queue ( user_id, status, rowid )` replacing the old queue/status indexes.
- **Tests first:** isolation tests for `jobStore`, `summaryRuns`, `linkRuns`, `linkSuggestions`; route isolation for every jobs route (get, list, draft update, save, discard, regenerate, retry, paste text, accept/reject suggestions, source/download renderers) and for the vault folder routes; a worker test where two users' jobs run with their own default model/prompt (owner from `job.user_id`); sweeper expires jobs of both users; interrupted-job recovery covers all users; save writes through `vaultRootFor( userId )`.
- **Code:** create `repositories/system.repository.ts` with `findNextRunnableJob()`, `markInterruptedJobs`, `markInterruptedLinkingJobs`, `findExpiredJobs( now )` moved from `jobStore` (decision 1), each returning rows with `user_id`. Convert the four repos. Thread `userId` through all ~25 `jobs.service` exports, `jobs.controller`, `vault.service`/`vault.controller`; `moveTo` in `jobs/lifecycle.ts` and `markStatus` take the owner (check `moveTo`'s call to `updateJob` when starting). `worker.ts`, `runJob.ts`, `summarizeJob.ts`, `linkJob.ts`, `sweeper.ts`, `recoverInterruptedJobs` use `job.user_id`; the job paths drop the shim. `queueJob( userId, … )` is also called by `inbox.service` (pass the HTTP user; background `feeds`/`gmailSources` callers keep the shim until 4.3). Add `services/vault.service.ts: vaultRootFor( userId )` returning `config.vaultPath` (decision 3), used by `listFolders`, `defaultFolderFor`, `saveJob`. Feed/Gmail-source lookups inside `queueJob`/`toPublicJob` stay unscoped until 4.3 (noted in the log).
- **Existing tests expected to change:** the ~18 job/worker/lifecycle files get a user in fixtures (`jobStore.*`, `summaryRuns`, `linkRuns`, `linkSuggestions` repos; `jobs.service`, `inbox.service`, worker, sweeper, `pipeline.integration`).
- **Commit:** `feat(0.9-4.2): per-user jobs and runs`.

## 4.3 Feeds, inbox, Gmail
- **Schema:** `feeds`, `feed_items`, `gmail_account` (PK `user_id`, `id = 1` check removed), `gmail_sources`, `gmail_messages`, `job_postings`, `posting_sightings`, `extraction_runs`; `feeds_active_url` unique on `( user_id, feed_url ) WHERE deleted_at IS NULL`; `feed_items_inbox ( user_id, status, added_at )`; `gmail_messages_status ( user_id, status, added_at )`; `dedupe_key` unique per `( user_id, dedupe_key )`; `job_postings_seen ( user_id, first_seen_at )`. Scope the shared `ALERT_EMAIL_SELECT` SQL and the feed/source health LEFT JOINs by `user_id`.
- **Tests first:** isolation for the six repos plus `extractionRuns` (same feed URL, same item GUID, same Gmail message ID for two users is allowed; each user's inbox, counts and dismiss-all only touch their own rows); route isolation for feeds, inbox (summarize/dismiss another user's item → 404), Gmail account, Gmail sources; Gmail OAuth: the `state` map stores `{ userId, origin, expiresAt }`, a state issued for A is refused when B's session completes it, the client cache is per user, the redirect URI is `<origin>/api/gmail/oauth/callback` from `currentOrigin( req )` (unknown origin → 400); intake poller: due feeds/sources of two users are each checked and queue jobs for the right owner; Gmail source checks skip users whose account isn't connected.
- **Code:** `system.repository.ts` gains `listDueFeeds( now, intervalMinutes )` and `listDueGmailSources( now, intervalMinutes )` (decision 1; interval from `app_settings`). Convert the repos; thread `userId` through `feeds`, `inbox`, `gmail`, `gmailSources` services and controllers, `gmail/auth.ts` (`createConsentUrl( userId, origin )`, `completeConsent( userId, … )`, `getGmailClient`, `withGmail`, `disconnect`) and `gmail.client.ts`. `config.gmail.redirectUri` and its localhost stub go. The `gmail_connection` health subject ID becomes the user's ID (not `'default'`) in `gmail/auth.ts` and `status.service`; `getStatus` takes `userId` so feed/source/connection rows are the caller's own. `checkFeed`/`runCheck`/`queueAutomatically` use the row's `user_id`; the intake poller drops the shim. Complete the `queueJob` lookups from 4.2 (`findFeedById( userId, … )` etc.). Fixtures (`test-support/gmailSources.fixture.ts`) take a user.
- **Commit:** `feat(0.9-4.3): per-user feeds, inbox and Gmail`.

## 4.4 Health split
- **Schema:** `health_status`, `health_errors` get nullable `user_id` and exactly `CHECK ( ( kind IN ( 'agent', 'whisper', 'backup' ) ) = ( user_id IS NULL ) )` (the schema test matches that exact text); `health_errors` index includes the user; key stays `( kind, subject_id )`.
- **Tests first:** `health.repository` isolation (user rows only visible to the owner; app rows only when `includeApp`); the CHECK rejects a user kind with null and an app kind with a user; `recordCheck( null, … )` for agent/whisper/backup and `recordCheck( userId, … )` for feed/source/connection; `GET /api/status` as admin shows app rows plus own sources, as a member only own rows, `failing_count` counts what the caller sees; refresh and errors behaviour per decision 6; `POST /api/backups` as member → 404; `openDatabase`'s set-aside and pre-migration copies are recorded as a `backup` check after the database opens (the 2.4 deferral).
- **Code:** convert `health.repository` (positional `userId`), `recordCheck( userId | null, subject, result, at? )`, all its callers (`feeds`, `gmailSources`, `gmail/auth.ts`, `backup.service`, `health.service`), `status.service`/controller/routes taking the caller, `serviceMonitor` and `runServiceChecks` write app kinds with `null`, `requireAdmin` on the backups route, `server.ts` records the open-time backup check. `test-support/health.fixture.ts` takes a user (or null).
- **Commit:** `feat(0.9-4.4): per-user health and admin-only app checks`.

## 4.5 Melete

## 4.6 Module gating and closing the guards
- **Tests first:** `middleware/requireModule.test.ts` (member without the module → 404 with the same body as an unknown route; admin always passes); table-driven `routes/moduleGating.routes.test.ts` (and the isolation matrix) over every router: Transcriber routes (jobs, feeds, inbox, Gmail, Gmail sources, vault folders, link suggestions, summary prompts) 404 for a Melete-only user, `/api/melete/*` 404 for a Transcriber-only user, shared routes (settings, models, prompt profiles, status) work for both; prompt-profile lists and lookups filter by `purpose` (summary + linker need Transcriber; the two Melete purposes need Melete; a disallowed profile ID is 404); `PUT /api/settings` with a key of a missing module is a 404 and saves nothing (decision 7); queued work for a module-off user stays untouched. Un-skip "has no unconverted tables left" in the schema guard and the "list is empty" test in the signature guard.
- **Code:** `middleware/requireModule.ts`; mount per path prefix in `app.ts` (`app.use( '/api/jobs', requireModule( 'transcriber' ) )` and so on, after checking each router's actual paths), **not** on the shared `/api` mount, which would gate settings/models/status too. Add module filtering to `prompts.service`/`settings.service`. Delete the `UNCONVERTED` arrays, `services/interimOwner.ts` and its test. Update `apps/server/CLAUDE.md` (ownership rules, `system.repository.ts`, `requireModule`, per-user scan clock, no caches left unkeyed; list every module-level cache found in the log).
- **Commit:** `feat(0.9-4.6): module gating and closed ownership guards`.

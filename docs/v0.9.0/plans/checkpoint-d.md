# Checkpoint D plan: Phase 5 (vaults, agent and loops)

## Context
Checkpoint C left every table owned and every route gated, but all users still share one vault (`vaultRootFor( userId )` returns `config.vaultPath`, marked INTERIM) and the loops take "the oldest" item with no eligibility or fairness (`system.repository.ts` header says so). Checkpoint D (ADRs 0063, 0064, 0043; TRD §6, §7, §11.1, §11.2) gives each user a vault under one `/vaults` mount, lets them claim or create it, makes the agent resolve `vault_dir`, and makes the loops respect modules, removed users and round-robin. Tasks run 5.1 → 5.4; one commit each (`feat(0.9-5.x): …`, co-author trailer), pushed. After each task: `pnpm test`, `pnpm lint`, `pnpm typecheck` in every touched folder (`apps/server`; 5.3 also `packages/shared` and `apps/agent`'s pytest/ruff/mypy as its CLAUDE.md lists; `pnpm build` at the end). `pnpm e2e` is not required before F and still fails until 8.1; the report says so.

Every task: failing tests first and watch them fail for the right reason, least code, refactor green, tick Status, add a log line in `tasks.md` listing every existing test file changed, commit, push. No new dependency is needed.

## Decisions to confirm (not settled by the TRD/ADRs)
1. **`claimNextJob` picks and stamps; it does not move the job.** TRD §6.1 says it moves the job "to its first running status through `moveTo`". Today the first move belongs to the source adapter (`downloading` for video, `fetching` for article, via `markStatus`), and `runnable` states are `queued`, `summarizing` and `linking`, which have no "first running status". So `claimNextJob( now )` selects the next job by round-robin, sets that user's `last_job_started_at` in the same transaction, and returns `{ job row with user_id }`; the worker keeps calling `runJob`. Only one worker runs, so there is no double-claim. This replaces `findNextRunnableJob` (which gets deleted along with the jobs.service wrapper's name; the wrapper becomes `claimNextJob`).
2. **Startup vault check (`server.ts`).** `assertVaultWritable( config.vaultPath )` and `resolveFolder( …, defaultNoteFolder )` can't run without a user. 5.1 replaces them with: `config.vaultsPath` must exist, be a directory and be readable and writable, else the server exits as today. `DEFAULT_NOTE_FOLDER` is no longer created at startup; it is only a fallback label and `saveJob` already creates the folder it writes to (to be confirmed by reading `writeNote` when implementing; if it doesn't, `listFolders`/`saveJob` create it per vault on first use).
3. **`VAULT_PATH` removal.** `VAULT_PATH` becomes an ignored variable (`ignoredEnv`, logged at `warn`, like `GOOGLE_REDIRECT_URI`); `VAULT_HOST_PATH` is replaced by `VAULTS_HOST_PATH` in Compose, `.env.example`, `e2e/run.sh` and the override. README is rewritten in 8.2 (not here); `apps/server/CLAUDE.md` is updated here.
4. **"Open in Obsidian" link** (`obsidianUrl( config.obsidianVaultName, … )` in `meleteReview.service.ts:147`) stays global in 5.1, so a member's link would name Naresh's vault. The TRD is silent. Recommendation: leave it, record it in the 5.1 log line and the checkpoint report as a follow-up for Naresh (options: admin-only link, or use the user's `vault_dir` as the vault name). I won't change it without his say.
5. **Cross-user `system.repository.ts` functions are renamed per TRD §6.1:** `findNextRunnableJob → claimNextJob`, `findExpiredJobs → listExpiredJobs`, `markInterrupted*` + `requeueGenerating → listRestartRequeue` semantics kept (restart requeue stays a set of UPDATEs, all users, no eligibility). Existing callers and the tests that moved there in 4.x change by rename only.
6. **Repository `vault_dir` writes already exist** (`setVaultDir`, `clearVaultDir` returning `vault_taken`), so 5.2 needs no new repository function except a read of all claimed dirs (`listClaimedVaultDirs()`) for the unclaimed-folder list.

## 5.2 Vault onboarding
- **Tests first:** `vaultOnboarding.service.test.ts` against a temp `vaultsPath` and `routes/me.vault.routes.test.ts` (names follow the existing `me.routes` test):
  - `GET /api/me/vaults`: lists only directories directly under the root whose names match `VaultDir`, not symlinks, not files, not hidden/invalid names (`My Vault`, `.obsidian`, `UPPER`), and not any user's `vault_dir`; 409 when the caller already has a vault.
  - `POST /api/me/vault { vault_dir }`: claims an existing, unclaimed folder; refuses a missing folder, an invalid name (`../x`, `a/b`, empty), a symlink (even to a folder inside the root), a folder whose `realpath` leaves the root, an already-claimed folder (409 "That vault is already taken"), and a caller who already has a vault (409). **Claim race:** two users claim the same folder, the first wins and the second gets the 409 from the `UNIQUE` constraint (via `setVaultDir`'s `vault_taken`), with no second check-then-write.
  - `POST /api/me/vault/new`: creates the folder non-recursively and claims it; an existing folder → 409 and it is left alone; a failed claim (taken by someone between `mkdir` and claim, forced in the test by a second user inserting the same name) removes the empty folder it made but never a folder it didn't make.
  - `GET /api/me` shows the new `vault_dir`; all three routes work for a member with no modules (they are open routes like `/api/me`, not behind `requireModule`).
- **Code:** `services/vaultOnboarding.service.ts` (`listUnclaimedVaults( userId )`, `claimVault( userId, vaultDir )`, `createVault( userId, vaultDir )`), `listClaimedVaultDirs()` in `users.repository.ts` (decision 6), controller functions in `me.controller.ts` and three routes in `me.routes.ts`; request bodies parsed with `VaultDir`-based schema from `@mnemosyne/shared` (add a `ClaimVaultBody`/`VaultListResponse` there only if `auth.ts` doesn't already export them; check first, and if a contract is missing stop and ask since it would be a contract change not in TRD §2). `Lstat` for the symlink and the `realpath` containment check reuse `isInside` from `clients/vault.client.ts`.
- **Commit:** `feat(0.9-5.2): vault onboarding`.

## 5.4 System repository, eligibility, round-robin loops
- **Tests first** (`system.repository.test.ts`, loop tests per TRD §11.1 "Loops"):
  - `claimNextJob( now )`: two users each with queued jobs alternate A, B, A, B by `last_job_started_at` (nulls first, then `users.created_at`); a user with a Transcriber switch off, a removed (`status != 'active'`) user, and a Melete-only member are never claimed; the admin always is; restoring the user or the module makes their queued job claimable again; a `summarizing` or `linking` job counts as runnable; with one user the order is the old oldest-first (`rowid`).
  - `claimNextGeneration( now )`: same for `melete_notes` queued, requiring Melete eligibility **and** a `vault_dir`; uses `last_generation_started_at`; a Melete user with no vault is skipped; a `generating` note is never claimed twice.
  - `listDueFeeds`/`listDueGmailSources`: join `eligible_users` (Transcriber); sources only with a connected account (already true); a module-off or removed user's feed is not returned; ordering unchanged (least-recently-checked first).
  - `listExpiredJobs`: all users, no eligibility filter (a removed user's expired job is still returned); `listRestartRequeue`: stuck jobs and generating notes of all users.
  - `linkJob.test.ts`: owner with no `vault_dir` → job reaches `ready_for_review` with `link_state = 'failed'` and the error "Choose a vault first", no agent call, no link run; with a vault the call sends `vault_dir`.
  - `worker.test.ts`/`meleteGenerator.test.ts`/`intakePoller.test.ts`/`sweeper.test.ts`/`serviceMonitor.test.ts`: the worker calls `claimNextJob` and runs the owner's job; a module-off user's queued job stays `queued` and untouched across several passes and runs after the module is switched back on; the intake poller does not check a removed user's feed and still records health with the owner's `user_id`; the sweeper deletes expired jobs of every user plus sessions; the service monitor writes only `user_id NULL` rows (existing behaviour, asserted).
  - Restart requeue test: jobs stuck in running states fail with "Interrupted by restart", linking jobs go to review with a link error, `generating` notes return to `queued`, for two users.
- **Code:** `system.repository.ts` gets `claimNextJob( now )` (decision 1; in one transaction: select via `eligible_users` where `module = 'transcriber'`, order by the user's `last_job_started_at IS NOT NULL`, `last_job_started_at`, `users.created_at`, then the job's `rowid`; update the user's stamp), `claimNextGeneration( now )` (replaces the zero-argument version), eligibility joins in `listDueFeeds` and `listDueGmailSources`, `listExpiredJobs` and `listRestartRequeue` (renames, decision 5); `jobs.service.ts` exposes `claimNextJob` instead of `findNextRunnableJob`; `worker.ts`, `meleteGenerator.ts`, `intakePoller.ts` callers updated; `linkJob.ts` "Choose a vault first" branch (before the agent call; the job moves to review through the normal `failLinking` path); `apps/server/CLAUDE.md` (worker, system repository, eligibility); `docs` log. Add `users.repository` helpers only if the claim queries need them (they shouldn't: the stamps are columns of `users` updated inside `system.repository.ts`).
- **Existing tests expected to change:** `system.repository.test.ts` (renames; earlier "today's semantics" tests keep their cases), `worker.test.ts`, `jobs.service.test.ts` (rename), `meleteGenerator.test.ts`, `intakePoller.test.ts`, `linkJob.test.ts`, `pipeline.integration.test.ts` if it calls `findNextRunnableJob`. Listed in the log.

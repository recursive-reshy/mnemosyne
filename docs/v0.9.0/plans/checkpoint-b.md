# Checkpoint B plan: Phase 3 (sign-in and sessions)

## Context
Checkpoint A left the baseline schema with `users`, `user_modules`, `sessions` and `app_settings`, and no code that uses them. Checkpoint B adds the sign-in half of v0.9.0 (ADR 0061, ADR 0065 for seeding, ADR 0068 for the 401/JSON contract): config, the four auth repositories, `seedUser`, origin handling, the Google client behind an interface, sessions and middleware, and the auth routes with `GET /api/me`. At the end every existing `/api` route sits behind `requireUser`, but data tables still have no `user_id` (that is Checkpoint C). Order is fixed: 3.1 → 3.2 → 3.3 → 3.4 → 3.5 → 3.6. After each task: `pnpm test`, `pnpm lint`, `pnpm typecheck` in `apps/server` (and `packages/shared` / `apps/web` typecheck if touched), tick Status, add a log line, commit `feat(0.9-3.x): …` with the co-author trailer, push. `pnpm e2e` is not required (starts at F), but note it will fail from 3.6 until 8.1 adds `E2E_TEST_SIGNIN`; say so in the report.

## Decisions taken with Naresh
- **Interim env (3.1):** keep `VAULT_PATH` required and `config.vaultPath` in use until 5.1, which removes it with the `warn`. `GOOGLE_REDIRECT_URI` is removed from the schema in 3.1 and warned about if set; until 4.3 `config.gmail.redirectUri` is derived as `http://localhost:<PORT>/api/gmail/oauth/callback`, so Gmail keeps working. Nothing breaks between commits. This is a deliberate deviation from the task row's wording ("`VAULT_PATH` removed"); mention it in the report.

## Findings from reading the code
1. **`config.gmail` becomes non-null.** `GOOGLE_CLIENT_ID`, `GOOGLE_CLIENT_SECRET` and `TOKEN_ENCRYPTION_KEY` are now required, so `config.gmail` is always an object. Its null checks in `gmail/auth.ts`, `services/gmail.service.ts`, `gmailSources.service.ts`, `status.service.ts` stay for now (lint may flag them as unnecessary; if so remove the dead branches and their tests in 3.1 and list them in the log). `vitest.config.ts` `test.env` gains the new required variables; config tests that built env objects update.
2. **`google-auth-library` is already in the lockfile** at 11.3.1 (under `@googleapis/gmail`); add it to `apps/server/package.json` at that exact version so no new package enters the tree. First check its `OAuth2Client` API (`generateAuthUrl`, `getToken`, `verifyIdToken`, `generateCodeVerifierAsync`) against TRD §4.3 (context7 docs). If it differs in a design-changing way, stop and ask.
3. **`seedDefaults` is used only by `database.ts` and `database.test.ts`.** It runs inside `openDatabase`, so today every test gets seeded profiles for free. Replacing it with `seedUser` means tests that need profiles get them through `createTestUser` (which calls `seedUser`).
4. **Shared profile rows until Phase 4.** Profiles have no `user_id` yet, so `seedUser` seeds the shared rows once: it reuses `seedProfile` (which skips by `seed_key`) and writes `default_profile_id` only if absent, so a second user adds nothing. Per-user seeding arrives in 4.1. The per-user part to test now: it runs in one transaction, is idempotent, and does not overwrite a changed `default_profile_id`.
5. **Settings stay global.** `settings.repository.ts` (`getSetting( key )`) is converted in 4.1, not here. 3.2 adds only the four new repositories.
6. **`logContext.ts`** has a fixed field list; add `user_id`. Per TRD §4.6 `requireUser` calls it once the user is known. Express middleware runs outside `withLogContext`'s callback scope, so use `storage.enterWith`-style or wrap `next()` in `withLogContext( { user_id }, next )`; the latter is the pattern already used.
7. **Errors:** `errors.ts` has `NotFoundError`, `ConflictError`, `ValidationError`, `UnprocessableError`. 401 needs a new `UnauthenticatedError` (→ `{ error: 'unauthenticated' }`) and 415 a `UnsupportedMediaTypeError`, both handled in `errorMiddleware`; add with tests in 3.5.
8. **Test helper scope.** All route tests use `request( app )` from Supertest. `test-support/auth.ts` exposes `createTestUser( { role, modules, vault_dir } )` (inserts user, modules, runs `seedUser`) and `signedIn( agent, user )` (inserts a session row and sets the cookie). Existing route tests wrap their agent with it in 3.6; list every changed file in the log. Mutating requests in existing tests that send no body must send `{}` once `jsonOnly` lands (Supertest `.send( {} )` sets JSON).

## Task 3.2: auth repositories and `seedUser`
- **Tests first** (red: modules missing), one test file per repository plus `seedUser.service.test.ts`, two-user style where it applies:
  - `users.repository`: `insertUser` lower-cases the email and rejects a duplicate; `findUserByEmail` / `findUserById`; one-admin index rejects a second admin (member fine); `bindGoogleSub` sets once and a duplicate `sub` is rejected; `setVaultDir` and `clearVaultDir` (unique `vault_dir` conflict surfaces as an error the caller can detect); `updateUser` partial fields; `touchSignIn`; `listUsers` ordering (admin first, then name); `deleteUser` cascades to `user_modules` and `sessions`.
  - `userModules.repository`: `listModules` / `setModules` replaces the set; empty set clears; unknown module rejected by the CHECK.
  - `sessions.repository`: insert/find by hash, `touchSession`, `deleteSession`, `deleteSessionsForUser` (only that user's), `deleteExpiredSessions( now )` (strictly expired only).
  - `appSettings.repository`: `getAppSetting` / `setAppSetting` typed on `AppSettingKey` (undefined when unset; overwrite).
  - `seedUser`: in one transaction (a failure part-way leaves nothing); seeds all `SEEDED_PROFILES`, the linker and the two Melete profiles with version 1 and `default_profile_id`; a second call and a second user add no duplicates and don't overwrite a changed default; rolls back on error.
- **New:** `users.repository.ts`, `userModules.repository.ts`, `sessions.repository.ts`, `appSettings.repository.ts`, `services/seedUser.service.ts` (moves the `seedProfile` / `seedDefaults` logic out of `database.ts`). **Delete** `seedDefaults()` and its call in `openDatabase`; `database.test.ts`'s `seedDefaults` tests move to `seedUser.service.test.ts`.
- **Fallout:** tests relying on pre-seeded profiles (e.g. `promptProfiles.routes.test.ts`, `jobs`/`summarizer` tests, `database.setup.ts`) need them. Cheapest: `database.setup.ts` calls `seedUser` for a throwaway user after `openDatabase`, keeping every existing assertion valid until 4.1 gives profiles an owner; that seeding line is the single thing 4.1 removes. List any test that needed other changes.
- The signature guard and schema guard (2.5) already exempt `users`, `user_modules`, `sessions`, `app_settings` repositories by name; confirm they still pass and add the new files to the exempt list only if the test requires it.
- Commit: `feat(0.9-3.2): auth repositories and seedUser`.

## Task 3.3: `requestOrigin`
- **First** (no code): read Tailscale's current `tailscale serve` docs for what headers reach the backend; then ask Naresh to run one request through the tailnet address and paste the headers the app sees. Record both in the `tasks.md` log. If it forwards `Host` unchanged and no `X-Forwarded-*`, use `Host` and treat the `https` origin with that host as the match (TRD §4.2).
- **Tests first** (`middleware/requestOrigin.test.ts`; red: missing): loopback peer with `X-Forwarded-Proto` / `X-Forwarded-Host` → that origin if in `APP_ORIGINS`; loopback peer without forwarded headers → socket scheme + `Host`; non-loopback peer ignores forwarded headers (spoof attempt) and uses `Host`; unknown origin → a typed `UnknownOriginError` (auth routes turn it into 400 "This address isn't configured in APP_ORIGINS"); IPv6 loopback `::1` and `::ffff:127.0.0.1` count as loopback; comma-separated forwarded values use the first; the allow-list comparison is on the normalised origin.
- **New:** `middleware/requestOrigin.ts` exporting `requestOrigin( req, origins )` (pure, takes the list so tests need no config) plus a thin wrapper reading `config.appOrigins`. Add the 400 mapping in `errors.ts`.
- Commit: `feat(0.9-3.3): request origin from forwarded headers`.

## Task 3.5: sessions and middleware
- **Tests first** (red: missing):
  - `session.service.test.ts`: `createSession` returns a 32-byte base64url token and stores only its SHA-256 hex; cookie header attributes (`HttpOnly`, `SameSite=Lax`, `Path=/`, `Max-Age` = `SESSION_DAYS`, `Secure` only for an `https` origin); lookup by token; expired → not found; sliding: a touch within the hour changes nothing, after the hour extends `expires_at` and `last_seen_at`.
  - `middleware/auth.test.ts` on a tiny Express app: no cookie, unknown token, expired session, removed user → 401 `{ error: 'unauthenticated' }` and a clearing `Set-Cookie`; valid → `req.user = { id, role, modules, vault_dir }` (modules from `user_modules`, all modules for the admin); cookie parser handles multiple cookies, `=` inside values, malformed pairs; sliding re-sends the cookie at most hourly; `requireAdmin` answers 404 to a member (TRD §5.2) and passes the admin; `currentUser( req )` throws when `req.user` is absent; log context carries `user_id` for the rest of the request (`getLogContext()` inside a handler) and never the email.
  - `jsonOnly.test.ts`: POST/PUT/PATCH/DELETE under `/api` without `application/json` → 415; with `application/json` (and charset suffix) passes; GET/HEAD/OPTIONS unaffected.
  - sweeper test: `deleteExpiredSessions` is called each sweep and only expired rows go.
- **New:** `services/session.service.ts`, `middleware/auth.ts` (`requireUser`, `requireAdmin`, `parseCookies`, `currentUser`), `middleware/jsonOnly.ts`, `types/express.d.ts` (or the repo's equivalent location) augmenting `Request` with `user`; `UnauthenticatedError` and `UnsupportedMediaTypeError` in `errors.ts` with `errorMiddleware` mapping; `user_id` added to `LogContext`; the sweeper (`jobs/` or wherever the sweep loop lives; find it with `grep -rn "sweep"` when starting) calls `deleteExpiredSessions( now )`.
- Commit: `feat(0.9-3.5): sessions, requireUser and jsonOnly`.

## Task 3.6: auth routes and `GET /api/me`
- **Tests first** (red: routes missing) using the fake sign-in client and a real in-memory database:
  - `GET /api/auth/google`: sets the signed `mnemosyne_oauth` cookie (`HttpOnly`, `SameSite=Lax`, 10 minutes, HMAC-SHA256 with the HKDF key from `TOKEN_ENCRYPTION_KEY`, info `mnemosyne-oauth-cookie`), redirects to the URL the fake built with the matching `state`; `returnTo` accepted only if it starts with `/` and not `//` (also reject `/\`, absolute URLs) else `/`; unknown origin → 400.
  - `GET /api/auth/callback` (every TRD §11.1 case): verified known active user → binds `google_sub`, creates the session, sets the cookie, `touchSignIn`, redirects to `returnTo`; second sign-in with the same `sub` works; a different `sub` for the same email → `/signin?error=not_allowed`; unverified email → `not_allowed`; unknown email with users present → `not_allowed`; empty table + email equals `ADMIN_EMAIL` → admin inserted with `seedUser` in one transaction (and a failure in `seedUser` leaves no admin row); empty table + other email → `not_allowed`; second admin-email sign-in after the admin exists doesn't create another; `removed` user → `not_allowed`; bad or missing `state`, missing cookie, tampered cookie signature, expired cookie → `expired` or `failed` as TRD says; Google error (`SignInError`) → `failed`; the oauth cookie is cleared on every outcome; warnings logged without tokens or the email.
  - `POST /api/auth/signout`: deletes the session row, clears the cookie, 204; without a session still 204.
  - `GET /api/me`: `Me` shape (admin has every module; member's modules; `vault_dir` null) validated with the shared `Me` schema; 401 without a session.
  - `app.test.ts`: middleware order (health and auth reachable unauthenticated; every other `/api` route 401 without a cookie; static web routes not behind `requireUser`; unknown `/api` path still 404 when signed in).
- **New:** `services/auth.service.ts`, `routes/auth.routes.ts`, `routes/me.routes.ts` (`GET /api/me` only; the vault routes arrive in 5.2), `test-support/auth.ts`. **Edit** `app.ts` to the TRD §4.6 order: `requestLog` → `express.json` → `jsonOnly` → `healthRoutes` → `authRoutes` → `requireUser` → `meRoutes` → existing routers → `notFoundHandler` (admin routes join in 6.1).
- **Fallout (the large part):** every existing route test (`jobs`, `feeds`, `inbox`, `gmail`, `gmailSources`, `vault`, `settings`, `models`, `promptProfiles`, `status`, `backups`, `melete`, `app*`, `web.routes`, plus any integration-style test using `app`) signs in through `signedIn( agent, createTestUser(…) )`, and bodyless mutating requests send `{}`. Flag in the log if any existing test cannot sign in cleanly.

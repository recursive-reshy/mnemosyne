## Findings (need your eye)
1. **Learning root is saved through `useSettings().updateSettings`** (`UpdateSettingsBody` already has `melete_learning_root`, shared `summarizer.ts:75`). Saving it changes what `GET /api/melete/today` returns, so the mutation's `onSuccess` in `LearningRootSetup` invalidates `meleteKeys.all` (the settings hook only sets the settings cache). Done in the component via `useQueryClient`, or by adding the invalidation inside `useSettings`. I plan the latter (one line, and the Melete cache can never be stale after a root change). The server rejects a root that is not in the vault (409/400 with a message), which `LearningRootSetup` shows as an error alert.
2. **`FolderPicker` needs a `defaultFolder` string** ([FolderPicker.tsx:21](apps/web/src/components/FolderPicker/FolderPicker.tsx#L21)). For the learning root I pass `''`-safe handling: current root or the vault top. I need to read how `FolderPicker` treats an empty default before writing the test; if it can't, I'll pass the current root, or the first top-level folder, as the default and treat a pick of that same path as a normal pick (value always set explicitly in this dialog). If that needs a `FolderPicker` change (e.g. optional `defaultFolder`), that is small but it touches an existing component, so I'll flag it in the log line.
3. **Polling scope (TRD §11.1):** `useMeleteSubject` and `useMeleteNote` poll every 2 s while any note is `queued` or `generating`. For the note page the "any note" is that one note. `useMeleteToday` does not poll. I follow `useJob`'s `refetchInterval` function style, reusing `POLL_INTERVAL_MS` from `useJob.ts`.
4. **Cache updates from mutation responses** (TRD §11.1): `useEnrollSubject` and `useSetNoteEnrolled`/`regenerate`/`retry` return the subject/note response, so they `setQueryData` on the subject or note key, and invalidate `meleteKeys.today` (counts changed). `useSetNoteEnrolled` returns a `GetMeleteNoteResponse`, so the subject's note list is invalidated (not patched) to keep the list and note in sync. `useUpdateSubject` returns `{ subject }` and patches the subject key's `subject` field and invalidates today. `useDropQuestion` returns `{ question }` and patches that question in the note key, then invalidates the note (its count changes).
5. **No `MeleteReview` yet.** 7.2 adds the route `melete/review` pointing at a minimal placeholder? No: a placeholder component would be throwaway. Plan: 7.2 registers only `melete`, `melete/subjects/:subjectId` and `melete/notes/:noteId` as their pages land (7.3–7.5), and adds the `melete/review` route in checkpoint G with `MeleteReview`. Until then the Today page's **Start review** / per-subject **Review** link to `/melete/review[?subject=id]`, which falls to the `*` fallback and redirects to `/`. That is a dead link between checkpoints F and G, accepted because both land before use; tell me if you'd rather hide the buttons until G. TRD §11.1 lists the review route; this defers it one checkpoint.
6. **Drawer test and `AppShell` test list drawer items** ([NavDrawer.test.tsx](apps/web/src/components/NavDrawer/NavDrawer.test.tsx), [AppShell.test.tsx](apps/web/src/components/AppShell/AppShell.test.tsx)); TRD §13.1 allows updating tests that list every drawer item. Each change goes in the 7.2 log line.
7. **File size rule (~150 lines):** `MeleteSubject` and `MeleteNote` would exceed it, so each is split: `MeleteSubject` → `SubjectControls` (Enroll all/Unenroll all, auto-enroll switch, new-per-day field), `MeleteNoteRow`; `MeleteNote` → `MeleteQuestionItem`. `MeleteToday` → `LearningRootSetup`, `MeleteSubjectRow`. Names follow the existing `Melete*` prefix; all are components with their own tests.
8. **Today link target for subjects:** `/melete/subjects/:id`; note rows link to `/melete/notes/:id`. A note page's back link goes to its subject (`note.subject_id`).
9. **Obsidian link:** `GetMeleteNoteResponse` has no `obsidian_url`, only `MeleteReviewItem` does. TRD §11.2 says "Open in Obsidian (when the URL is set)" on `MeleteNote`, but the note response carries no URL. Options: add `obsidian_url` to `GetMeleteNoteResponse` (contract + server change, outside this checkpoint) or build the URL in the web from a vault name the web doesn't have. **I need your decision**; my recommendation is to add `obsidian_url: string | null` to `GetMeleteNoteResponse` (server `getNote`, routes tests, shared schema/tests) as a first sub-step of 7.5, with an ADR-free note in the log since TRD §2.1/§10 say the response is `{ note, questions }`. Alternatively defer the link to G. (This is a contract change, which the root CLAUDE.md says to stop and ask about.)
